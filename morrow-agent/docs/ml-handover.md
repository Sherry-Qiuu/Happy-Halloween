## 2 数据从哪来：四层采集阶梯

| 层 | 内容 | 状态 | 触发点 |
| --- | --- | --- | --- |
| **L0** | 每次保存的整份 state 快照（gzip，按用户按天） | ✅ 已上线 | `PUT /api/data` → `_archive_state()` |
| **L1** | 提案生命周期：shown / accepted / rejected / edited | ⬜ 待做 | 前端上报 + `/api/agent/event` |
| **L2** | 块级事件：planned / started / completed / moved / dropped | ⬜ 待做 | 拖拽、勾选、开始 |
| **L3** | 语言特征（长度、语气词比例、正式度、是否问句） | ⬜ 待做 | 每轮对话 |

L0 落在 `MORROW_DATA_DIR/snapshots/<user_id>/<YYYY-MM-DD>.jsonl.gz`，每行：

```json
{"ts": 1730772000.0, "sha": "ab12cd34ef56ab78", "bytes": 8421, "state": {"tasks": [...], "goals": [...]}}
```

保留 90 天，启动时清理；删号级联删除。

**L1/L2 的事件再没有，也能先用 L0**：相邻快照做 diff 就能还原出"新增/删除/改期/完成"，只是精度到"保存时刻"。

## 3 指标定义（照抄，别自创）

| 指标 | 由什么算 | 公式 | 可靠起点 |
| --- | --- | --- | --- |
| 估时偏差 K | 完成块的计划时长 vs 实际时长 | `median(actual / planned)` | n ≥ 5 |
| 块完成率 P(L) | 按块长分桶的完成/计划 | `completed / planned` per bucket | 每桶 n ≥ 5 |
| 时段完成率 R(h) | 按开始小时分桶 | 同上 | 每桶 n ≥ 5 |
| 启动延迟 D | 任务创建 → 首次开始 | `median(days)` | n ≥ 5 |
| 中断率 I | 块内被挪/被切的比例 | `moved_or_split / planned` | n ≥ 5 |
| 采纳率 | 提案被接受的比例 | `accepted / shown` | n ≥ 20 |
| 采纳后完成率 | 被接受的块里实际发生的比例 | `completed_after_accept / accepted` | n ≥ 20 |
| 语言风格 | L3 特征 | 众数 + 占比 | n ≥ 10 句 |

**类型是投影**：P3 = K>1.4，P5 = I 高，P8 = 所有 n 都小。系统里不要建"类型"这个实体。

## 4 建模顺序（别跳步）

1. **可解释基线**：分位数 + Beta 后验（`sched_profile` 已实现）——先确认它能跑出数
2. **收缩**：`w = n/(n+k)`，k≈5。n 小时信先验，n 大时信个人
3. **漂移检测**：3 次同侧残差 >1.5×MAD 才判漂移（已实现）。单次 >3×MAD 只记 outlier
4. **轻量模型**（仅当门槛满足）：逻辑回归 / GBDT 预测"这个块能不能做成"
5. **校准**：Platt / isotonic，因为排布要的是概率，不是分数
6. **端到端 / 在线微调：不做**（理由见 7）

## 5 门槛（硬性，不到就别上）

- 单指标 **n ≥ 30**，且总交互 **≥ 200 轮**
- 必须**前向验证跑赢基线**：只用 t 之前的数据预测 t+1
- 线上 A/B：胜出才切
- 指标不掉：区间覆盖率 0.7–0.9，Brier 不上升

## 6 评估协议

- **点预测**：MAPE（按周滚动）
- **区间**：80% 区间的覆盖率；<0.7 视为过度自信，自动放宽
- **概率**：Brier / 对数损失
- **反例集**（必须手工建，否则一定过拟合）：连续加班周、病假月、假期、新用户首周、用户主动删掉目标
- **上探块**：每两周放一个比预测高 20% 的块，记录突破率；>30% 说明模型太保守

## 7 三条红线

1. **不训练、不微调模型**：用户注销后权重里的痕迹删不掉（合规硬伤）、不可解释、小数据会灾难性遗忘
2. **模型输出不能回灌画像**：对话是内生数据，拿它更新"能力"指标等于循环论证。"你晚上效率低"如果是模型先说的，用户点头不算证据
3. **画像只改"怎么排"，不改"给不给"**：一旦画像影响供给（少派任务、锁目标），就变成隐形降权，必须可见化

## 9 已知的坑

- **快照是整份覆盖**：diff 时按 `id` 匹配，**不要按数组位置**
- **时区**：业务全用 Asia/Shanghai；快照文件名用 UTC 日期，导出时统一换算
- **demo 数据污染**：`web/demo-seed.js` 会灌演示数据，导出时要按 `isDemo` 或账号白名单剔除
- **空 state**：首次保存可能为空，直接跳过
- **画像会倒退**：用户删数据后 `portrait.derive` 重算就会变小——这正是要事件流的原因
